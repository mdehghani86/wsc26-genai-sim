Companion application

A tutorial on Generative AI and Simulation Modeling Integration

A live, in-browser walk-through of the five-stage GenAI-driven simulation framework from the paper: Problem Formulation, Creation, Execution, Experimentation, and Evaluation. Each stage holds three rising-complexity LLM contributions. Every Python cell on this site runs in your browser via Pyodide — no backend, no installs.

Read the paper PDF · draft
Phase 0
Problem formulation
A structured prompt that returns a three-row schema: problem, scope, KPIs. The artefact every later phase is judged against.
Phase 1a · live
Input modelling
Upload arrival data or pick a demo trace. The LLM proposes candidate distributions; scipy runs the chi-square, KS, and Anderson-Darling tests; the test wins.
Phase 1b
Model creation
From the Phase 0 schema and the Phase 1a fitted distribution, generate a runnable SimPy model via a five-row structured prompt (role, goal, scenario, inputs, output) protected by a five-check validation gate.
Phase 1c
Agentic AI via MCP
Stage 1.3 — Agentic Construction. The LLM constructs the simulation by calling typed tools (define_resource, define_process, run, query_kpis) over the Model Context Protocol, instead of emitting a one-shot file.
Phase 2
Execution
Run the SimPy model and watch per-pool ρ, Lq, Wq update live with M/G/c theory comparison. Three LLM capabilities layer on top: Entity Characterization, Orchestration (LLM-in-the-loop bed assignment), Prediction.
Phase 3
Experimentation
Three rising-complexity contributions: Summary Generation (figure selection + narrative), Scenario Ideation (factors and levels from the brief), Optimisation (LLM-driven parameter search with explicit caveats).
Phase 4
Evaluation
Closes the loop with Reproducibility (every figure regenerable from the repo), Validation (cross-checks against M/G/c bounds and Arena/Simio), and Benchmarking (paired-seed frontier-LLM comparison).
Connectivity spine
Stage 0 → Stage 1 (Input modelling → Model generation → Agentic construction) → Stage 2 → Stage 3 → Stage 4. Every page tells you which artefact it consumed and which artefact it produces.

Phase 0

Problem formulation

Phase 0 produces no code. It produces a written agreement on three items: the problem to be solved, the scope and boundaries of the system under study, and the key performance indicators (KPIs) the simulation will be judged against. Every later tab consumes this schema unchanged.

Prompt

I am planning a discrete-event simulation of an emergency department. Help me formulate the study as a structured problem statement.

Notes small community hospital, two triage tiers, the team wants to evaluate staffing and routing rule changes.

Search recent literature (2023–2025) on emergency-department simulation studies and pull common KPIs.

Return a single table with three rows: Problem definition, Scope & boundaries, and KPIs. Keep each cell to two or three short sentences.

Response
ElementStatement
1Problem definition Reduce length of stay in the emergency department and identify whether triage-rule changes or staffing changes deliver the larger improvement under fluctuating arrival rates.
2Scope & boundaries From walk-in arrival to admit-or-discharge. Two triage tiers (urgent, non-urgent), a shared imaging and laboratory pool, and fixed bed pools. Ambulance routing, no-shows, and inpatient bed flow are out of scope.
3KPIs Mean and 95th-percentile length of stay; door-to-doctor time per triage tier; bed and imaging utilisation; daily throughput.
This produces
A three-row schema. Row 2 (scope) feeds Model creation. Row 3 (KPIs) feeds Experimentation. Row 1 (problem) anchors the Execution stage.

    Phase 1b · vibe coding with a validation gate
    
        
    Model creation
    
        
    A five-part structured prompt produces a SimPy file; Pyodide runs it; a five-check validation gate decides whether the artefact may travel forward to Phase 2. Off-the-shelf packages such as Simio or Arena enforce these invariants at draw time on a canvas. Here we enforce them after the fact, automatically, on probabilistic LLM output.

          Five-part structured prompt
          role · goal · scenario · inputs · output
        
    
        
    
          
    
            
    RoleSimulation engineer.
    
            
    GoalProduce a runnable SimPy file for the Phase 0 problem.
    
            
    ScenarioED with two triage tiers (urgent, non-urgent), shared imaging, fixed bed pools. Walk-in arrival to admit-or-discharge. Ambulance routing, no-shows, and inpatient bed flow are out of scope (copied from the Phase 0 scope row).
    
            
    InputsArrival generator from Phase 1a (a single Python expression). Service-time distributions: triangular for treatment, gamma for imaging.
    
            
    OutputOne Python file, no dependencies beyond SimPy and the standard library. One simpy.Resource per pool, one worker process per server slot, per-patient and per-pool metrics, an event log.

          3
          Validation gate (five checks; all must pass)
          all passed
        
    
        
    
          
      
            
    • Process logic. Patient flow matches the Phase 0 scope row end to end (walk-in → triage → treatment → admit-or-discharge).
      • 
            
    • Connectivity. Each producer wires into the declared consumer; no orphan resources.
      • 
            
    • Parallel vs sequential. A pool with capacity c serves c patients in parallel; not one at a time behind a manager process. (One SimPy worker process per bed slot.)
      • 
            
    • Distributions. Sampled service times match the Phase 1a fit in mean, variance, and support.
      • 
            
    • Theory. Realised ρ, Lq, Wq within tolerance of Erlang-C and Allen-Cunneen across a 1-8 by 1-12 capacity grid.
      • 
          
    
          
    If any check fails, the failing check is appended to the next prompt verbatim and only the affected section is regenerated. Iterations are bounded; if three rounds do not pass, the case is handed off to the multi-agent or MCP path.
    
        
    
      
    

      
    
        
    Hands off to

    Stage 1.3 · alternative path
    
          
    Agentic construction via MCP
    
          
    Three failed gate rounds escalate the case to the agentic-construction route. The LLM stops emitting one-shot files and instead issues typed calls (define_resource, define_process, wire, run, query_kpis) against a small simulation API. Feedback arrives at every step instead of after the whole file. See Section 5.3 of the paper.
    
            
      
    
    
    

    
    
    
      
    
        
    Phase 2
    
        
    Execution
    
        
    Run the SimPy ER model produced in Phase 1b. Per-pool utilisation, queue length, and time-in-system update live. Three LLM capabilities — Entity Characterization, Orchestration, and Prediction — layer on top of the same execution loop.
    
      
    

      
    
        
    
          
    Entity Characterization
    
          
    After the run, the LLM narrates each patient's path through the system — severity, route, wait, and outcome — in plain English suitable for a clinical brief.
    
        
    
        
    
          
    Orchestration
    
          
    The LLM acts as the dispatcher. When a bed frees up, it picks which queued patient gets it, using context the FIFO rule cannot encode.
    
        
    
        
    
          
    Prediction
    
          
    The LLM forecasts the next-window arrival burst and treatment duration from the live state, so the simulator can pre-position resources.

    Key metrics
    
        
    

        
    Per-pool comparison vs M/G/c theory
    
        
    
          Note on the theory column. The "Theory" values use the Allen-Cunneen M/G/c approximation. It is exact for M/M/c (Cs² = 1) and known to underestimate Wq by up to 25-30% for low-CV service distributions like the triangular(20,30,45) and triangular(10,15,25) used here (Cs² ≈ 0.026 and 0.035). When the simulation is above the theory by that margin, the simulation is the more accurate value, not a bug.

    Phase 3 · Section 7 of the paper
    
        
    Experimentation
    
        
    Design the scenario set, sweep parameters, and turn results into something a reader can act on. Three rising-complexity LLM contributions: Summary Generation (figure selection plus a short written interpretation), Scenario Ideation (factors and levels proposed directly from the Phase 0 brief), and Optimisation (LLM-driven parameter search, used only on small designs with cheap evaluations).

    Stage 1.3 · Agentic construction (Section 5.3)
    
        
    Agentic AI via Model Context Protocol
    
        
    A simpy-mcp server exposes the simulator as a small set of typed tools. The LLM does not write Python and does not see the source. It calls define_resource, define_process, wire, run, and query_kpis, and the server answers. The session below is recorded — but the server is real and runs in your browser via Pyodide, so every reply you see is the actual server output for that call.

    Position
    
        
    PDEVS-LLM (WSC 2025) and SimLLM (Jan 2026) are the closest neighbours and remain code-generation-flavoured. This tab is the protocol-flavoured complement: instead of asking the LLM to emit a SimPy file, we expose a typed tool surface and let the LLM construct the model through calls.
    
      
    
    
    

    
    
    
      
    
        
    Phase 4 · Section 8 of the paper
    
        
    Evaluation
    
        
    Close the loop with three rising-complexity LLM contributions: Reproducibility (every figure, prompt, and result regenerable from this repo, exercisable in your browser), Validation (KPIs cross-checked against closed-form M/G/c bounds and a commercial Arena or Simio reference), and Benchmarking (the same harness run against multiple frontier LLMs on paired seeds — the bed-assignment policy table from Section 6.2 is the worked instance).
